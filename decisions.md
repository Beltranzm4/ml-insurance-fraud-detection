# Decisiones del proyecto

| Fecha | Decisión | Motivo |
|---|---|---|
| 2026-09-29 | Usar `fraud_oracle.csv` y descartar el dataset sintético de Kaggle (car-insurance-fraud-detection) | Datos con patrones reales, AUC baseline 0,84 frente a 0,76 y mayor mejora sobre el azar (4,3× frente a 2,9×). El otro tenía importes incoherentes (28 % con total < claim) y era sintético |
| 2026-09-29 | Estructura, `.gitignore` y entorno virtual replicados de retail-sales-analysis | Coherencia entre proyectos del portfolio |
| 2026-09-29 | Supuestos de coste: investigar = c·V con c entre 1 % y 5 % del valor V de la reclamación; fraude no detectado = L·V con L entre 3,5 y 4 (el 100 % de V más costes de reposición, legales, disputas y reputación). Caso base c = 3 %, L = 3,75 | Aportados por el autor (estimaciones del sector financiero/online, no específicas de seguro de auto). El dataset no tiene importes, así que solo importa la razón L/c (70–400) y se hace análisis de sensibilidad |
| 2026-09-29 | Umbral de decisión teórico p* = c/L (entre 0,25 % y 1,4 %) | Investigar una reclamación con prob. de fraude p compensa si p·L·V > c·V |
| 2026-09-29 | Enfoque: solo lo necesario para el modelo de fraude; los costes solo fijan el umbral | Indicación del autor |
| 2026-09-29 | `Age = 0` → NaN (sin columna indicadora) | Las 320 filas con `Age = 0` son exactamente las de `AgeOfPolicyHolder = "16 to 17"`: es un código de desconocido. Inventar un valor sesgaría el modelo y eliminar `Age` perdería detalle en 15.100 filas. La pertenencia al grupo ya la recoge `AgeOfPolicyHolder`. Los modelos de árboles tratan NaN de forma nativa; la LogReg imputará la mediana dentro del pipeline |
| 2026-09-29 | Proyecto íntegramente en español | Decisión del autor |
| 2026-09-29 | Eliminar la fila sin fecha de reclamación (`MonthClaimed = '0'`) | Caso único (1 de 15.420), sin fecha y con `Days_Policy_Claim = 'none'`: el modelo no puede aprender de categorías con un solo caso |
| 2026-09-29 | Corregir erratas de `Make` (Accura, Mecedes, Nisson, Porche) | No conviven con la grafía correcta, así que no cambian el modelo; se corrigen por legibilidad |
| 2026-09-29 | Categorías con n < 100 → "Otras", dentro del pipeline (`OneHotEncoder(min_frequency=100)`) | Los IC 95 % muestran que por debajo de ~100 casos la tasa de fraude es ruido (Nissan n=30: 0,1 %–17 %) y provocaría sobreajuste. Se hace en el pipeline para que el recuento use solo train (sin fuga) |
| 2026-09-29 | Eliminar `NumberOfSuppliments` y `PoliceReportFiled` | Posible fuga (datos que pueden conocerse después de abrir la reclamación) y señal casi nula (V de Cramér 0,034 y 0,016): quitarlas da seguridad sin perder rendimiento |
| 2026-09-29 | Mantener `Fault` como supuesto; en la Fase 3 comparar el modelo con y sin ella | Señal alta (V 0,131; 7,9 % frente a 0,9 % de fraude) con explicación lógica previa al fraude, pero el momento en que se conoce la culpa no está documentado |
| 2026-09-29 | Eliminar `PolicyType`; usar `VehicleCategory` y `BasePolicy` | `PolicyType` equivale uno a uno al par `VehicleCategory` + `BasePolicy` (misma información). Con `PolicyType`, 4 categorías tendrían < 100 casos y al agruparlas en "Otras" se mezclarían tasas de fraude muy distintas; con el par no se pierde nada |
| 2026-09-29 | Limitación: en 4.987 pólizas Liability, `PolicyType` dice "Sedan" y `VehicleCategory` dice "Sport" | Una de las dos está mal etiquetada y no hay documentación para saber cuál |
| 2026-09-29 | Eliminar `Year` | Solo 3 valores (1994–1996), asociación casi nula (V 0,025) y el modelo se aplicará a años futuros que nunca ha visto: solo aprendería una tasa por año, no un patrón repetible |
| 2026-09-29 | Crear `retraso_meses` = (`MonthClaimed` − `Month`) mod 12, con 3 o más agrupado en 3 | La tasa de fraude sube con el retraso (5,5 % → 7,0 % → 10,5 %); el modelo no tendría que deducirlo de dos columnas separadas. Aproximación (±1 mes) porque solo hay mes y semana |
| 2026-09-29 | Eliminar `PolicyNumber` | Identificador único |
| 2026-09-29 | Las decisiones que dependen del target (filtro de variables, agrupación de categorías raras) se toman solo con train (notebook 02) | Evitar que el test influya en el modelo (fuga). Limitación: el EDA del notebook 01 se hizo con todos los datos |
| 2026-09-29 | Split 80/20 estratificado (`random_state=42`), test intacto hasta la evaluación final | Mantener el 6 % de fraude en ambos conjuntos. No es temporal: `Year` solo tiene 3 valores y se eliminó |
| 2026-09-29 | Conservar solo variables con p < 0,05 en chi² (Mann-Whitney para `Age`) calculado en train; eliminar 9 (`DayOfWeek`, `WitnessPresent`, `RepNumber`, `WeekOfMonth`, `WeekOfMonthClaimed`, `DayOfWeekClaimed`, `NumberOfCars`, `DriverRating`, `MaritalStatus`) | Sin evidencia de relación con el fraude. Con 28 tests, 1–2 falsos positivos posibles: las de p entre 0,01 y 0,05 son las menos seguras |
| 2026-09-29 | Ordinales (con orden explícito) / one-hot con `min_frequency=100` / numéricas sin tocar; `Age` conserva NaN; el preprocesador vive en `src/preprocesamiento.py` | La imputación de `Age` para la LogReg se hará en su pipeline (los árboles manejan NaN). Limitación: como el umbral se aplica sobre train (80 %), Saab y Dodge (108–109 casos en total) quedan agrupadas en "Otras" |
| 2026-09-29 | Ablación (HGB, CV 5×3): `Fault` −0,082 de PR-AUC al quitarla (37 % del rendimiento), `BasePolicy`+`VehicleCategory` −0,052, edades −0,018; el resto ≤ 0,003 (ruido) | Sabemos qué sostiene el modelo |
| 2026-09-29 | Entrenar y reportar dos versiones: con `Fault` y sin `Fault` | No sabemos cuándo se registra la culpa (sin documentación); un único número podría estar inflado |
| 2026-09-29 | No usar `class_weight` ni SMOTE por ahora | `class_weight='balanced'` no mejora la PR-AUC (Δ −0,002 a −0,009, dentro del ruido ≈ 0,02) porque esta métrica depende del orden de las probabilidades, no de su escala. Si dar más peso a los fraudes reales no ayuda, los sintéticos (SMOTE) difícilmente lo harán |
| 2026-09-29 | Resultados base (PR-AUC, CV 5×3): con `Fault` HGB 0,222 / LogReg 0,169; sin `Fault` HGB 0,140 / LogReg 0,145 | Sin `Fault` un modelo complejo no aporta sobre el lineal |
| 2026-09-29 | Comparación con valores por defecto (PR-AUC, con/sin `Fault`): HGB 0,222/0,140, LightGBM 0,222/0,142, XGBoost 0,217/0,132, RandomForest 0,193/0,111, LogReg 0,169/0,145. Ajustar solo LightGBM y LogReg; descartar RandomForest y XGBoost | Los boosting empatan; RandomForest y XGBoost sobreajustan sin `Fault`. LightGBM es rápido y tiene parámetros anti-sobreajuste; la LogReg es la mejor sin `Fault` |
| 2026-09-29 | Ajuste con Optuna (CV 5×3): LightGBM 50 intentos, LogReg 20 (solo `C`, solver lbfgs). LightGBM ajustado es el modelo final en ambas versiones: PR-AUC validación 0,245 (con `Fault`) y 0,167 (sin) frente a LogReg 0,169 y 0,146 | Ganó en las dos versiones. Árboles pequeños (12–17 hojas), learning rate bajo y ~50 % de variables por árbol frenan el sobreajuste. Se descartó `saga` (L1/L2) por lentitud y las interacciones manuales (+0,001–0,005, ruido) |
| 2026-09-29 | Probabilidades usadas sin recalibrar | Calibración verificada por deciles en predicciones out-of-fold de train (p. ej. 21,6 % predicho frente a 22,0 % real) |
| 2026-09-29 | Umbral: se reportan dos criterios, por coste (c/L, caso base 0,8 %) y por capacidad (top-k %) | Con los costes supuestos investigar es muy barato: con `Fault` el umbral base investiga el 67–70 % y descarta un tercio perdiendo ≈ 1 % del fraude; sin `Fault` compensa investigarlo todo. Por eso el uso principal del modelo es ordenar reclamaciones con capacidad limitada |
| 2026-09-29 | Resultado final en test (una sola evaluación): con `Fault` PR-AUC 0,257 / ROC-AUC 0,833 / recall top 20 % 0,595; sin `Fault` PR-AUC 0,150 / ROC-AUC 0,748 / recall top 20 % 0,459 | Modelos guardados en `models/` |
| 2026-09-29 | Interpretabilidad con SHAP (TreeExplainer, test): `Fault`, `BasePolicy` y `VehicleCategory` concentran la decisión; el caso de mayor riesgo (85 %) lo disparan categorías raras con mucho fraude (cambio de domicilio 2–3 años, franquicia 500) pese a culpa de tercero; los fraudes no detectados son pólizas Liability | Modelo coherente con el negocio; punto ciego documentado |
